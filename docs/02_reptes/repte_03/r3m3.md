# R3M3. Primer cas d'ús complet

## En una frase

Reconstruïx un flux real d'`R2` dins del framework: entrada, validació, regla,
BBDD, resposta visible i prova del cas correcte i de l'error.

## Visor del microrepte

| Camp | Valor |
|---|---|
| Repte | `R3` |
| Sessió | `R3S3` |
| Microrepte | `R3M3` |
| RA avaluat | `RA8` (`RA8.d`, `RA8.e`, `RA8.g`) |
| Autocorrecció | `r3-s03-primer-cas-us-complet` |
| Producte | Primer recorregut end-to-end persistent i server-rendered |

## Què heretes d'R3M2

- El framework arranca.
- La BBDD, els models i les migracions existixen.
- Hi ha dades inicials i una lectura real.
- El primer flux ja està identificat i acotat.

R3M3 reutilitza eixa base. No tornes a crear el projecte ni substituïsques els
models per arrays temporals.

## Mínim obligatori

Si el flux crea dades, el recorregut recomanat és:

```text
GET formulari → POST → validació → regla → ORM/BBDD → redirecció → resultat
```

Ha d'incloure:

- formulari server-rendered amb dades del domini;
- protecció CSRF del framework;
- validació real en servidor;
- errors visibles i conservació de valors aprofitables;
- una regla pròpia del projecte fora de la presentació;
- escriptura amb el model, relació o repositori existent;
- redirecció després de l'èxit;
- confirmació, detall o llistat que torne a llegir la BBDD;
- cas positiu i cas invàlid sense efectes parcials.

Si el flux aprovat és de consulta, ha de processar una interacció significativa
—cerca, filtre o detall validat— i no quedar-se en un llistat estàtic. Abans de
tancar R3 hauràs de tindre almenys un flux d'escriptura server-rendered.

## Repartiment de responsabilitats

| Peça | Responsabilitat |
|---|---|
| Ruta | Mètode HTTP, URL, nom i manejador |
| Formulari/DTO/Request | Contracte de l'entrada |
| Validador | Regles de format, valors permesos i missatges |
| Controlador/view | Coordinar entrada validada, operació i resposta |
| Servei o regla | Decisió del domini que no depén d'HTML |
| Model/ORM/repositori | Llegir o escriure dades persistents |
| Plantilla | Presentar camps, errors i resultat; no consultar la BBDD |

No és obligatori crear una classe de servei per cada `if`. Sí que has d'evitar
que una única ruta, controlador o plantilla concentre tot el treball.

## Passos de treball

1. Escriu quin flux d'R2 reconstruïxes i quin resultat persistent produïx.
2. Dibuixa el recorregut de la petició abans de programar.
3. Implementa el `GET` i la plantilla del formulari.
4. Implementa el `POST`, CSRF i validació en servidor.
5. Situa la regla del domini en la peça adequada.
6. Guarda només dades validades mitjançant l'ORM.
7. Redirigix i mostra l'estat llegit novament de la BBDD.
8. Prova el cas correcte, un error de validació i una regla manipulada.

## Proves mínimes

| Cas | Què has de comprovar |
|---|---|
| Formulari | El `GET` mostra camps reals i token CSRF |
| Cas positiu | Resposta esperada i canvi persistent en BBDD |
| Entrada invàlida | Error visible, valors aprofitables i cap INSERT/canvi parcial |
| Regla de domini | Casos i fronteres importants |
| Identificador manipulat | Error controlat o `404` quan corresponga |
| Resultat final | La resposta mostra l'estat real guardat |

## Evidències mínimes

- Codi de ruta, validació, controlador/view, regla, model i plantilla.
- Prova funcional o registre reproduïble del cas positiu.
- Prova funcional o registre reproduïble de l'entrada invàlida.
- Comprovació directa de la BBDD abans/després.
- Documentació del flux heretat, responsabilitats i ordres de prova.
- Commits i registre d'IA si correspon.

## Què no és suficient

- Un llistat sense interacció ni escriptura.
- Validar només amb atributs HTML.
- Mostrar “guardat correctament” sense comprovar la BBDD.
- Fer el cas feliç i no provocar cap error.
- Consultar la BBDD directament des de la plantilla.
- Concentrar validació, regla, SQL i HTML en una sola peça.
- Afegir autenticació, API o el segon flux abans de tancar este recorregut.

## Ampliació opcional

- Prova unitària de la regla de negoci.
- Casos de frontera addicionals.
- Pujada de fitxer quan el flux sense fitxer ja siga atòmic i estiga provat.

## Fora d'abast

No toca encara el segon flux, autenticació completa, autorització, API ni una
refactorització total.
